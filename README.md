# Waduge Inn

The owner-confirmed layout has four rooms on each floor, with a kitchen on both floors. The 2nd Floor has two Triple Rooms (three guests each) and two Single Rooms (one guest each). The existing 1st Floor room keeps its saved details; the other three await bed types/capacities. New room prices remain unset until supplied. An unset rate/capacity is displayed as pending and cannot be booked, including through a direct API request. Whole-floor totals remain unknown until all rooms on that floor are configured. Admins can fill these fields later; no zero-price placeholder is used. `scripts/register-floor-rooms.js` is the one-time, manually invoked inventory setup for these real rooms and is not run at application startup.

The guest interface presents Waduge Inn as a Nuwara Eliya property above Gregory Lake. The home page uses the two supplied landscape photos in its opening slider. `public/guest.css` supplies shared guest styling; `public/resort.css` styles the home page and `public/catalog.css` styles the separate room catalogue. Optional `PUBLIC_ADDRESS`, `PUBLIC_PHONE`, `PUBLIC_EMAIL`, and an HTTPS `PUBLIC_MAP_URL` in `.env` populate the contact section; contact buttons appear only when configured. The map link should be the actual hotel's pin. `WHATSAPP_NUMBER` supplies the WhatsApp contact link. Room prices use the existing `CURRENCY` setting; redesigning the site does not convert stored prices.

Rooms are grouped into **1st Floor** and **2nd Floor**. Choose the floor when adding a room, or use the floor selector on an existing room in the admin inventory table. Existing rooms default to 1st Floor on migration; assign the correct floors before accepting bookings. Active room or whole-floor bookings prevent moving the affected room. Guests can book an individual room or use **Select entire floor & book**. The full-floor nightly rate and guest capacity are the sums of that floor's registered rooms. Empty floors cannot be booked. A floor request creates one booking, one payment record total, and one private status link. Whole-floor reservations block every room on that floor for the dates, while any overlapping room reservation blocks booking the entire floor. Other floors and adjacent checkout/check-in dates remain available. A PostgreSQL range exclusion constraint enforces these rules even for concurrent requests and direct SQL inserts. Startup upgrades existing bookings without deleting them; restart the server to apply the migration.

**Book now** opens `/rooms.html`. Guests can browse room and entire-floor cards, or enter dates and guest count to see matching available options. Selecting a room opens `/booking.html?room=<room-id>`; an entire floor uses `?floor=1` or `?floor=2`. Dates and guest count carry through to the booking page, which checks availability again. Opening the booking page without a selection redirects to the catalogue. The homepage stays compact and has no room inventory or booking flow section.

Admins can add and edit real room names, types, prices, capacity, descriptions, floor assignments, and photo URLs. Photos can use HTTPS or a deployed `/assets/filename.jpg` path. Missing photos have an explicit placeholder; landscape photos are not used as room photos. Existing booking totals do not change when a room price is edited. Active reservations prevent moving the affected room between floors.

Bank transfer payments: set `BANK_NAME`, `BANK_BRANCH`, `BANK_ACCOUNT_NAME`, `BANK_ACCOUNT_NUMBER`, and `ADVANCE_PERCENT` (default 30) in `.env`, then restart. Existing prices retain their configured `CURRENCY`; changing currency does not convert them. Guests choose advance or full payment and send their booking request on WhatsApp. Admins use **Send bank details**, then press Send in WhatsApp. Guests send receipts in that chat; the website does not upload receipts or verify bank credits automatically. After checking the actual bank credit, use **Record verified payment** to enter the cumulative paid total and transfer reference. Corrections require a note and are recorded in `booking_payment_records`. Recording money does not confirm a booking: staff confirm separately, and the server requires the minimum advance first. Pending bookings remain reserved until manually cancelled or confirmed. Cancellation does not refund payments; staff arrange refunds separately. Guest status pages show verified payments and balance. The advance percentage is saved per booking, so changing the setting affects new bookings only. Missing bank settings disable bank-details links.

After saving a booking, guests see their stay details and can copy a private status link. The link opens `/booking-status.html#<secret>` without requiring an account and refreshes the status every 15 seconds while pending or confirmed. The secret stays in the URL fragment and is sent to `/api/booking-status` in an `X-Booking-Token` header, rather than a query string. The response excludes guest names and contact details and is not cached. Anyone holding the link can view the reservation summary, so guests should keep it private. Restart the server after upgrading: startup adds a unique random status token to new and existing bookings. Existing guests need a newly shared link; old references alone do not grant access.

To view the interface without a database, run `npm run preview`. Open http://localhost:3001 or http://localhost:3001/admin. This local preview skips admin login and shows empty room/booking lists. Saving changes is disabled. It binds only to the local computer and does not load database credentials.

Run `npm start` and open http://localhost:3000. The admin portal is at `/admin`.

For Supabase setup, open an active project in the dashboard, select **Connect → Session pooler**, and copy its exact PostgreSQL URI into `DATABASE_URL` in `.env`. Replace the password placeholder with the database password, URL-encoding special characters. The session pooler uses port 5432 and supports IPv4 networks. Do not guess the pooler hostname/region or substitute a Supabase API key. Restart the server after changing `.env`; startup creates/upgrades the tables automatically. Room and booking data stays behind the Express API: RLS is enabled with no public Data API policies. The server's database-owner connection can access these tables; anonymous Supabase API clients cannot.

Set `DATABASE_URL` and a long, unique `ADMIN_PASSWORD` in `.env` (see `.env.example`). Never commit `.env`. Admin access uses an HttpOnly session cookie, expires after eight hours, and is revoked on logout. Sessions are kept in memory, so restarting the server requires signing in again. Run one server instance; multiple instances require a shared session and rate limit store. Use HTTPS with `NODE_ENV=production` when hosting publicly.

Startup applies `schema.sql` in a transaction before accepting requests. The PostgreSQL `btree_gist` extension and `bookings_no_overlap_v2` constraint prevent overlapping pending/confirmed reservations, including concurrent inserts. Adjacent stays are allowed. If existing active bookings overlap, startup fails without deleting records: review and resolve the conflicting bookings before restarting. The database role must be able to install the extension and alter these tables.

New bookings require the booking guest's identity: Sri Lankan guests enter a NIC (12 digits or 9 digits followed by V/X); foreign guests enter a passport number. Identity details are stored with the booking and displayed to authenticated staff, and are omitted from WhatsApp messages and the public status lookup. Restart the server after updating to add the identity columns automatically; existing bookings retain empty identity fields.

Guests choose dates, select an available room, see the total, and save a pending request. Pending and confirmed bookings block overlapping reservations until staff cancel them. Pending requests never expire automatically. Staff must cancel abandoned requests to release rooms. Retrying an unchanged request uses the same reference to avoid duplicates. Startup clears old deadlines on pending requests; previously expired or cancelled bookings remain unchanged.

Set `WHATSAPP_NUMBER` in `.env` later to enable the WhatsApp flow. Use an international number such as `94771234567`. Without a number, bookings still save, and the interface clearly states WhatsApp is not configured. The guest clicks **Book via WhatsApp** once: the website saves the pending hold in the background and opens WhatsApp with the request message. The guest must press **Send** there. If the browser blocks the window, a fallback WhatsApp link appears with the saved reference. The message includes the reference, room, dates, price, guest count.

When staff click **Confirm**, the database is updated first. On success, WhatsApp opens with a prepared confirmation addressed to the guest's number; staff must press **Send**. A fallback link and a **Send confirmation** link on confirmed bookings allow retrying without changing the booking. Opening WhatsApp does not prove a message was sent or delivered. Sri Lankan local numbers starting with `0` are normalized to `94`; guests from other countries should enter their international number. Expired/cancelled requests never receive confirmation links.

Set `PUBLIC_BASE_URL` to the public website URL to include a staff link such as `/admin?booking=<reference>` in notifications. That link highlights and scrolls to the booking after sign-in; it does not grant access or confirm anything. A localhost URL cannot be opened by staff on another device. Admin sessions last eight hours and do not survive server restarts.

Automatic staff email is optional. Configure `RESEND_API_KEY`, `NOTIFICATION_FROM` (a verified Resend sender), `NOTIFICATION_TO`, and `PUBLIC_BASE_URL`. See [Resend's email API](https://resend.com/docs/api-reference/emails/send-email). New requests enqueue a durable notification in the same database transaction as the booking, even when email is not configured. A worker submits queued emails to Resend and retries failures with backoff up to eight attempts within 23 hours. Idempotency keys prevent duplicate submissions on retries. Provider acceptance is recorded; it does not prove delivery to the inbox. Missing configuration and unsent/failed counts appear in the admin dashboard. Requests older than 23 hours require manual follow-up and are not automatically emailed later. A successful booking response does not depend on email availability. Keep the server running for background email delivery.

Run `npm test` for local authentication, input validation, WhatsApp link, notification and script checks. To exercise real PostgreSQL constraints and concurrent booking requests, set `TEST_DATABASE_URL` to a separate test database and run `npm test`. The integration test creates and removes its own temporary schema; it never uses `DATABASE_URL`. Without `TEST_DATABASE_URL`, this test is skipped.

Run `node scripts/verify-setup.js` to apply startup migrations and check real inventory, availability, guest pages and admin login without creating bookings or sending notifications. Public hosting instructions are in [DEPLOYMENT.md](DEPLOYMENT.md). `/healthz` returns 200 only when the database query succeeds. The site has no online card payment gateway.
